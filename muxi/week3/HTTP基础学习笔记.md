## 00 学习导览

> 这本书回答的是一个很朴素的问题：我在地址栏里敲下一个网址，页面为什么就能显示出来？全书 11 章，真正撑起 HTTP 地基的是第 1、2、3、4、6 章 —— 也正好对应你想弄清楚的三件事：请求怎么走、TCP/IP 与 HTTP 是什么关系、URL / IP / 首部 / 负载 / 状态码这些概念分别指什么。

### 0.1 三块知识是怎么咬合的

不要把它们当成三份并列的清单。它们其实是一条链上的不同刻度：先有**协议分层**（TCP/IP），HTTP 才能坐在应用层上；HTTP 一旦开始通信，就必然表现为**一请求一响应**的报文；而报文里的每一行 —— 请求行、首部字段、空行、主体 —— 又都由 **URL、方法、首部、状态码、负载** 这些零件拼成。

```text
用户输入 URL
   |
   +-- ① 浏览器解析 URL ------ 得到 协议 / 主机 / 端口 / 路径
   +-- ② DNS 解析域名 -------- 域名 -> IP 地址      （应用层）
   +-- ③ TCP 三次握手 -------- SYN / SYN+ACK / ACK  （传输层）
   +-- ④ 发送 HTTP 请求 ------ 请求行 + 首部 + 空行 + 主体
   +-- ⑤ 服务器处理 ---------- Web 服务器 -> 应用程序
   +-- ⑥ 返回 HTTP 响应 ------ 状态行 + 首部 + 空行 + 主体
   +-- ⑦ 浏览器解析渲染 ------ 按 Connection 决定保持或断开
```

## 01 Web 请求的基本流程

> 先把“网页是怎么打开的”这件事讲透。这一章只回答一个问题：从你在地址栏敲下回车，到页面出现在屏幕上，中间到底发生了什么、谁在干活、用了哪些协议。把这条链路记住，后面所有概念都有了安放的位置。

### 1.1 两个角色：客户端与服务器

HTTP 协议和 TCP/IP 协议族内其他众多协议一样，用于**客户端和服务器之间**的通信。请求访问文本或图像等资源的一端称为**客户端**（client），提供资源响应的一端称为**服务器端**（server）。

> 在两台计算机之间使用 HTTP 协议通信时，在一条通信线路上必定有一端是客户端，另一端则是服务器端。
>
> —— 《图解HTTP》第 30 页

这里有个容易被忽略的细节：**角色是“每条连接”上的，不是机器的属性**。同一台电脑，在浏览器里访问别人时是客户端，跑着一个本地服务被别人访问时就是服务器。但就一条具体的 HTTP 通信线路而言，两端的角色是确定的 —— HTTP 能明确区分谁在请求、谁在响应。

**表 1-1　客户端与服务器端的分工**

| 角色 | 英文 | 职责 | 常见代表 |
| --- | --- | --- | --- |
| 客户端 | client | 主动发起请求，索取资源，并负责展示 / 消费结果 | 浏览器、爬虫、curl、手机 App |
| 服务器端 | server | 被动等待请求，解析并处理，返回资源与处理结果 | Nginx、Apache、Tomcat、Node 服务 |

> 💡 **一句话记住**　HTTP 通信是“**请求—响应**”式的问答：客户端先问，服务器才答。服务器不会主动给客户端发响应，这一点决定了后面要讲的“轮询”“WebSocket”为什么会出现。

### 1.2 一次请求 + 一次响应 = 一次 HTTP 通信

HTTP 协议规定，请求从客户端发出，最后服务器端响应该请求并返回。换句话说，**肯定是先从客户端开始建立通信的**，服务器端在没有接收到请求之前不会发送响应。

#### 1.2.1 请求报文长什么样

```http
GET /index.htm HTTP/1.1
Host: hackr.jp

（本例没有请求体）
```

**表 1-2　请求报文逐行拆解（原书第 31 页）**

| 组成部分 | 示例 | 含义 |
| --- | --- | --- |
| 请求方法 | `GET` | 请求访问服务器的类型，称为方法（method） |
| 请求 URI | `/index.htm` | 请求访问的资源对象，也叫 request-URI |
| 协议版本 | `HTTP/1.1` | 提示客户端使用的 HTTP 协议功能 |
| 请求首部字段 | `Host: hackr.jp` | 可选的附加信息，每行一个「字段名: 字段值」 |
| 空行 | （一个 CR+LF） | 分隔首部与主体的分界线，必不可少 |
| 内容实体 | （本例为空） | 要向服务器发送的数据，GET 请求通常没有 |

把这一行读成人话就是：**「请把某台 HTTP 服务器上的 /index.htm 这个页面资源给我。」**

#### 1.2.2 响应报文长什么样

```http
HTTP/1.1 200 OK
Date: Tue, 10 Jul 2012 06:50:15 GMT
Content-Length: 362
Content-Type: text/html

<html>
  ……
```

**表 1-3　响应报文逐行拆解（原书第 32 页）**

| 组成部分 | 示例 | 含义 |
| --- | --- | --- |
| 协议版本 | `HTTP/1.1` | 服务器对应的 HTTP 版本 |
| 状态码 | `200` | 请求的处理结果，三位数字 |
| 原因短语 | `OK` | 对状态码的简短文字解释 |
| 响应首部字段 | `Date`、`Content-Length`、`Content-Type` | 响应的附加信息 |
| 空行 | （一个 CR+LF） | 分隔首部与实体主体 |
| 实体主体 | `<html>……` | 真正返回给客户端的资源内容 |

> 💡 **结构上是完全对称的**　请求报文 = **起始行（请求行）+ 首部 + 空行 + 主体**；响应报文 = **起始行（状态行）+ 首部 + 空行 + 主体**。两者唯一的区别，只是起始行那一行写的东西不同。抓住这个对称性，报文结构就不用背了。

### 1.3 从输入 URL 到看见页面：完整的 7 步

下面这条链路，是所有 Web 请求的通用骨架。原书把前 4 步分散在第 1、2 章，这里按实际发生顺序串成一条。

**表 1-4　一次网页访问的 7 个步骤**

| 步骤 | 发生了什么 | 参与的协议 | 书中位置 |
| --- | --- | --- | --- |
| ① 解析 URL | 浏览器拆出协议方案、主机名、端口、路径、查询参数 | —（浏览器内部） | p27 |
| ② DNS 解析 | 把域名翻译成 IP 地址；先查本地缓存，再问 DNS 服务器 | DNS（应用层） | p22 |
| ③ 建立连接 | 与服务器 IP:端口 完成 TCP 三次握手 | TCP（传输层） | p21 |
| ④ 发送请求 | 组装并发送 HTTP 请求报文 | HTTP（应用层） | p31 |
| ⑤ 服务器处理 | Web 服务器接收请求，交给后端程序或直接读文件 | —（服务端） | p69 |
| ⑥ 返回响应 | 把结果组装成 HTTP 响应报文发回 | HTTP（应用层） | p32 |
| ⑦ 解析渲染 | 浏览器解析 HTML、请求图片 / CSS / JS，绘制页面 | HTTP + DNS + TCP | p41 |

#### 第 ① 步：解析 URL

浏览器先把这串字符拆成几个零件：用什么协议（http/https）、访问哪台主机（hackr.jp）、哪个端口（省略则用默认 80 / 443）、要哪个路径（/index.html）、带什么查询参数。拆完之后，浏览器才知道下一步该去找谁、走哪个门。URL 的七个组成部分见 3.1 节。

#### 第 ② 步：DNS 解析 —— 把“名字”换成“门牌号”

计算机之间真正通信靠的是 IP 地址，而人记不住 `192.168.1.1` 这种数字，所以有了域名和 DNS。DNS 服务提供**域名到 IP 地址**的解析，也支持从 IP 反查域名。

#### 第 ③ 步：TCP 三次握手 —— 先确认双方都能收发

HTTP 只管“说什么”，不保证“送得到”。保证送达是 TCP 的事。发请求之前，客户端与服务器要先握手确认通道可用：客户端发 `SYN`，服务器回 `SYN/ACK`，客户端再回 `ACK`。握手完成，连接建立，HTTP 报文才开始传。详见 2.3 节。

#### 第 ④⑤⑥ 步：一问一答

连接建立后，客户端发送请求报文；服务器解析请求，找到对应的资源或程序执行；再把结果按响应报文的格式写回去。注意：**一个请求对应一个响应**，浏览器要拿 10 张图片，就得发 10 个请求（这正是持久连接存在的理由，见 2.5 节）。

#### 第 ⑦ 步：解析与渲染

浏览器拿到 HTML 后开始解析，遇到 `<img>`、`<link>`、`<script>` 就再发起新的 HTTP 请求。所以打开一个页面往往不止一次请求 —— 打开开发者工具的 Network 面板，你会看到一长串。

> 💡 **为什么第 ⑦ 步值得单独说**　很多人以为“打开网页”是一次请求。实际上一个普通页面的请求数常常在几十到上百个之间，这就解释了 HTTP 为什么要设计持久连接、为什么要限制并发数、HTTP/2 为什么要多路复用。**请求数是理解 Web 性能的第一把钥匙。**

### 1.4 路上的中间人：代理、网关、隧道与缓存

HTTP 通信时，除客户端和服务器以外，还有一些用于**转发通信数据**的应用程序。它们配合服务器工作，把请求转发给下一站，再把响应转回来。

**表 1-5　四种通信数据转发程序（原书第 71–76 页）**

| 类型 | 英文 | 做什么 | 关键点 |
| --- | --- | --- | --- |
| 代理 | Proxy | 接收客户端请求并转发给服务器，同时把响应转回客户端 | 不改变请求 URI，直接发给持有资源的**源服务器**；经过时追加 `Via` 首部 |
| 网关 | Gateway | 转发其他服务器的通信数据，可把 HTTP 转成别的协议 | 客户端甚至察觉不到目标是网关；可连接数据库、对接支付系统 |
| 隧道 | Tunnel | 在相隔甚远的客户端与服务器之间中转，并保持双方连接 | 本身不解析 HTTP，请求原样中转；常用 SSL/TLS 加密，连接断开即结束 |
| 缓存服务器 | Cache Server | 代理的一种，保存资源副本，再次请求时直接返回 | 减少对源服务器的访问，节省流量与时间；需判断副本是否过期 |

代理还能级联：请求一路经过多台代理，每过一台就在 `Via` 首部里追加一条主机信息。所以 `Via` 既是“路过的证据”，也能用来避免请求在代理之间打转（回环）。

> 💡 **缓存为什么重要**　缓存的本质是“**用空间换时间**”：把响应副本存在离用户更近的地方。判断副本还能不能用，靠的是 `Cache-Control`、`Expires`、`Last-Modified`、`ETag` 这几个首部字段 —— 它们会在 3.7 节和 4.2 节反复出现。

### 1.5 HTTP 不保存状态，Cookie 如何补救

HTTP 是一种**不保存状态**，即**无状态**（stateless）的协议。协议自身不对请求和响应之间的通信状态进行保存 —— 发送过的请求或响应都不做持久化处理。

> 使用 HTTP 协议，每当有新的请求发送时，就会有对应的新响应产生。协议本身并不保留之前一切的请求或响应报文的信息。这是为了更快地处理大量事务，确保协议的可伸缩性，而特意把 HTTP 协议设计成如此简单的。
>
> —— 《图解HTTP》第 33 页

好处是服务器不用为每个用户维持上下文，一台机器能扛住海量请求；坏处是**服务器记不住你是谁**。购物车、登录状态、多步表单 —— 这些都要求“上一次”和“这一次”有关联。

于是引入了 **Cookie**：服务器在响应里用 `Set-Cookie` 首部通知客户端保存一段数据；客户端下次再访问同一站点时，自动把它放进请求的 `Cookie` 首部带回去。服务器对比自己保存的记录，就“认出”了这个客户端。

#### 一次完整的 Cookie 交互

```http
① 第一次请求（还没有 Cookie）
GET /reader/ HTTP/1.1
Host: hackr.jp

② 服务器下发 Cookie
HTTP/1.1 200 OK
Set-Cookie: sid=1342077140226724; path=/; expires=Wed, 10-Oct-12 07:12:20 GMT
Content-Type: text/plain; charset=UTF-8

③ 之后的请求（自动携带）
GET /image/ HTTP/1.1
Host: hackr.jp
Cookie: sid=1342077140226724
```

注意 `sid` 这个值本身没有任何含义 —— 它只是一个**句柄**，真正的用户状态存在服务器上。所以 Cookie 被盗，等于身份被盗，这也是后面 HTTPS 与 `HttpOnly` 要解决的问题。

**表 1-6　关于 Cookie 的四个常见疑问**

| 疑问 | 回答 |
| --- | --- |
| Cookie 存在哪？ | 客户端（浏览器）本地。服务器只保存“这个 sid 对应哪个用户”的记录。 |
| 关掉浏览器就没了？ | 不一定。`expires` 省略时是会话 Cookie，关浏览器即失效；指定了过期时间则持久保存。 |
| 为什么能保持登录？ | 每次请求自动带上同一个 sid，服务器据此查到上次的登录状态。 |
| 和 Session 什么关系？ | Session 是服务器端的“状态表”，Cookie 是这张表的钥匙（sid）。 |

> 💡 **本章小结**　① HTTP 是**请求—响应**式协议，客户端先问、服务器才答；② 一次通信 = 一个请求报文 + 一个响应报文，结构完全对称；③ 完整链路是 **URL → DNS → TCP → HTTP → 响应 → 渲染**；④ HTTP 无状态，靠 **Cookie** 补上状态管理。

#### 动手练一练

1. 打开任意网页，按 F12 → Network，刷新一次。找到第一条 `document` 请求，读它的请求行、`Host`、`User-Agent`，再对照表 1-2 把每一行都对上。
2. 在地址栏里故意访问一个不存在的路径（比如 `/no-such-page`），观察返回的 `404` 长什么样，响应体是什么。
3. 找一个需要登录的网站，登录前后各看一次 Network：登录请求里有什么，登录后的请求里多出了哪个首部。

## 02 TCP/IP 与 HTTP：协议的地基

> HTTP 不是一个孤零零的协议，它坐在 TCP/IP 协议族的最上层。不理解下面的三层，你就无法回答这些问题：为什么域名要变成 IP？为什么请求前要“握手”？为什么一个页面要发几十个请求？这一章把地基讲清楚。

### 2.1 协议、协议族与分层思想

计算机与网络设备要相互通信，双方就必须基于**相同的方法**：如何探测到通信目标、由哪一边先发起通信、使用哪种语言通信、怎样结束通信 —— 这些规则都需要事先确定。我们把这种规则称为**协议**（protocol）。

而把与互联网相关联的协议集合起来，就总称为 **TCP/IP**。注意这里有两个常见误解：
- **TCP/IP 不只是 TCP 和 IP 两个协议**，它是一整个协议族的统称，HTTP、DNS、FTP 都在里面。
- **HTTP 只是这个协议族的一个子集**，位置在最上面的应用层。

TCP/IP 协议族最重要的一点是**分层**。分层的好处很直接：如果互联网只由一个协议统筹，某个地方要改设计，就得把所有部分整体替换掉；分层之后只需替换变动的那一层，层与层之间的接口约定好，各层内部怎么实现可以自由改动。

> 💡 **分层的本质是“关注点分离”**　处于应用层的应用只需要考虑分派给自己的任务，而不需要弄清对方在地球上哪个地方、传输路线是怎样的、是否能确保送达 —— 那些是下面几层的事。写 Web 后端时你只关心 HTTP，正是分层带来的便利。

### 2.2 TCP/IP 的四层模型与封装

**表 2-1　TCP/IP 的四层结构（原书第 16–17 页）**

| 层 | 职责 | 代表协议 | 数据单位 |
| --- | --- | --- | --- |
| 应用层 | 决定向用户提供应用服务时通信的活动 | HTTP、DNS、FTP、SMTP | 报文 message |
| 传输层 | 对上层提供处于网络连接中的两台计算机之间的数据传输 | TCP、UDP | 报文段 segment |
| 网络层<br>（网络互连层） | 处理在网络上流动的数据包，选择一条传输路线把包送到对方 | IP、ARP、ICMP | 数据包 packet |
| 链路层<br>（数据链路层 / 网络接口层） | 处理连接网络的硬件部分：驱动、网卡、光纤等 | 以太网、PPP | 帧 frame |

发送端从应用层往下走，接收端则往应用层往上走。**每经过一层，就会被打上一个该层所属的首部信息**；接收端每经过一层，就把对应的首部消去。这种把数据信息包装起来的做法称为**封装**（encapsulate）。

```text
HTTP 报文
   ↓  传输层：加 TCP 首部（序号、端口号）
TCP 报文段
   ↓  网络层：加 IP 首部（目的 IP 地址、下一跳 MAC 地址）
IP 数据包
   ↓  链路层：加以太网帧头、帧尾
以太网帧  →  变成电信号，发送到网络上

接收端反过来逐层拆掉这些首部，最后把 HTTP 请求交到应用层。
```

**表 2-2　封装过程中每层追加的信息**

| 层 | 这一层加的首部里有什么 | 解决什么问题 |
| --- | --- | --- |
| 应用层 | HTTP 首部：方法、URI、状态码、各类字段 | 这次请求要什么、结果如何 |
| 传输层 | TCP 首部：序号、端口号 | 数据完整性、交给哪个进程 |
| 网络层 | IP 首部：目的 IP 地址、MAC 地址 | 送到哪台机器、下一跳走哪里 |
| 链路层 | 以太网首部：帧头、帧尾 | 在物理链路上真正发出去 |

### 2.3 与 HTTP 关系最密切的三个协议

#### 2.3.1 IP：负责把包送到对方手上

IP（Internet Protocol，网际协议）位于**网络层**。它的作用是把各种数据包传送给对方。要保证确实传送到，需要满足各类条件，其中两个最重要的条件是 **IP 地址**和 **MAC 地址**。

IP 地址指明节点被分配到的地址，**可以变换**；MAC 地址是网卡所属的固定地址，**基本不会更改**。两者可以配对使用。

IP 间的通信依赖 MAC 地址。通信双方在同一个局域网内的情况很少，通常要经过多台计算机和网络设备中转。中转时会利用下一站中转设备的 MAC 地址来搜索下一个中转目标，这时用的是 **ARP 协议** —— 根据通信方的 IP 地址反查出对应的 MAC 地址。

还有一个重要认知：**没有谁能全面掌握互联网中的传输状况**。在到达目标前的每一跳，路由器和交换机只能看到很粗略的传输路线，各自决定“下一站交给谁”。这种机制称为**路由选择**（routing）。

> 📖 **快递的比喻（原书用的就是这个）**　寄件人只要把包裹送到集散中心；集散中心看清地址，决定送往哪个区域的集散中心；那个区域的集散中心再判断能不能送到家。**谁都不知道全程，但包裹一定能到。**IP 的路由选择也是这样一跳一跳接力完成的。

#### 2.3.2 TCP：负责把数据可靠地送到

TCP 位于**传输层**，提供**可靠的字节流服务**。所谓字节流服务，是指为了方便传输，把大块数据分割成以**报文段**（segment）为单位的数据包进行管理；所谓可靠，是指能够把数据准确可靠地传给对方。

为确保数据能到达目标，TCP 采用了**三次握手**（three-way handshaking）策略。握手过程使用了 TCP 的标志 —— `SYN`（synchronize）和 `ACK`（acknowledgement）。

**表 2-3　TCP 三次握手**

| 次序 | 方向 | 标志 | 含义 |
| --- | --- | --- | --- |
| ① | 客户端 → 服务器 | `SYN` | 发送一个带 SYN 标志的数据包，请求建立连接 |
| ② | 服务器 → 客户端 | `SYN/ACK` | 回传带 SYN+ACK 标志的包，表示确认收到 |
| ③ | 客户端 → 服务器 | `ACK` | 再回传一个带 ACK 标志的包，握手结束 |

若在握手过程中某个阶段莫名中断，TCP 协议会**再次以相同的顺序发送相同的数据包**。此外 TCP 还有其他各种手段保证通信的可靠性（超时重传、滑动窗口、流量控制等）。

> 💡 **为什么“可靠”要付出代价**　每一次请求前都要先握手，意味着至少多出一个往返（RTT）的时间。这正是 HTTPS 要 2 个 RTT（TCP + TLS）、HTTP/3 改用 QUIC 追求 0-RTT 的原因。**可靠性与延迟，是传输层永恒的权衡。**

#### 2.3.3 DNS：负责把域名翻译成 IP

DNS（Domain Name System）服务是和 HTTP 一样位于**应用层**的协议，提供**域名到 IP 地址**之间的解析服务，也能逆向从 IP 地址反查域名。

为什么需要它？计算机既可以被赋予 IP 地址，也可以被赋予主机名和域名（比如 `www.hackr.jp`）。用户通常使用主机名或域名来访问，因为字母配数字比一组纯数字更符合人的记忆习惯；但计算机更擅长处理一长串数字。DNS 就是这两者之间的翻译官。

**表 2-4　三者在一次 HTTP 通信中的分工（原书第 23 页的「各种协议与 HTTP 协议的关系」）**

| 协议 | 所在层 | 一句话职责 | 在这次请求中的具体动作 |
| --- | --- | --- | --- |
| DNS | 应用层 | 域名 ↔ IP 地址的解析 | 把 `hackr.jp` 解析成 `192.0.2.1` |
| TCP | 传输层 | 可靠的字节流传输 | 三次握手建连，把 HTTP 报文切成段并保证送达 |
| IP | 网络层 | 把数据包送到目标主机 | 按 IP 地址一跳一跳地路由，用 ARP 找 MAC 地址 |

### 2.4 HTTP 的诞生与版本演进

1989 年 3 月，互联网还只属于少数人。CERN（欧洲核子研究组织）的蒂姆·伯纳斯-李博士提出了一种能让远隔两地的研究者们共享知识的设想，基本理念是借助多文档之间相互关联形成的**超文本**（HyperText），连成可相互参阅的 **WWW**（World Wide Web）。

这项设想落地成了三项技术：用 **HTML** 作为页面的文本标记语言，用 **HTTP** 作为文档传递协议，用 **URL** 指定文档所在地址。1990 年 11 月，CERN 研发出世界上第一台 Web 服务器和 Web 浏览器。

**表 2-5　HTTP 版本演进**

| 版本 | 时间 | 标准 | 关键变化 |
| --- | --- | --- | --- |
| HTTP/0.9 | 1990 | 无正式标准 | 只支持 GET，没有首部、没有状态码，只能传 HTML |
| HTTP/1.0 | 1996.5 | RFC1945 | 引入首部字段、状态码、多种方法；每次请求都新建并断开 TCP 连接 |
| HTTP/1.1 | 1997.1 | RFC2068 → RFC2616 | 默认持久连接、管线化、`Host` 首部必需、分块传输、Range 请求 |
| HTTP/2 | 2015 | RFC7540 | 「书外延伸」二进制分帧、多路复用、首部压缩（HPACK）、服务器推送 |
| HTTP/3 | 2022 | RFC9114 | 「书外延伸」改用 QUIC（基于 UDP），解决 TCP 队头阻塞，支持 0-RTT |

原书写作时 HTTP/2.0 还在制订中。今天回看，1.1 统治了近二十年，直到 2 与 3 才把“请求数太多”这个瓶颈从协议层面解决掉 —— 而它们解决的问题，正是 1.1 里持久连接和管线化没能彻底解决的。

### 2.5 持久连接与管线化

HTTP 协议的初始版本中，**每进行一次 HTTP 通信就要断开一次 TCP 连接**。当年传输的都是容量很小的文本，这样没什么问题；但随着 HTML 里图片越来越多，一次页面访问要发几十个请求，每次都建立并断开 TCP 连接就变成了巨大的浪费。

为此，HTTP/1.1 和一部分 HTTP/1.0 想出了**持久连接**（HTTP Persistent Connections，也称 keep-alive 或 connection reuse）的方法。

> 持久连接的特点是，只要任意一端没有明确提出断开连接，则保持 TCP 连接状态。
>
> —— 《图解HTTP》第 43 页

在 HTTP/1.1 中，**所有的连接默认都是持久连接**，但 HTTP/1.0 内并未标准化。想显式关闭，就发 `Connection: close`；在 HTTP/1.0 上想维持长连接，则要 `Connection: Keep-Alive`。

持久连接让**管线化**（pipelining）成为可能：从前发送请求后必须等待并收到响应，才能发下一个请求；管线化之后，不用等待响应也可直接发送下一个请求，做到同时并行发送多个请求。

**表 2-6　三种连接方式的对比**

| 机制 | 做法 | 收益 | 局限 |
| --- | --- | --- | --- |
| 短连接 | 一次请求一次连接，用完即断 | 实现简单 | 每次都要握手，开销大 |
| 持久连接 | 一次 TCP 连接上跑多次请求响应 | 省掉重复握手，页面更快 | 同一连接上的请求仍有先后顺序 |
| 管线化 | 不等响应就连发多个请求 | 比持久连接更快 | 响应必须按请求顺序返回，仍有队头阻塞 |

原书举的例子很直观：请求一个包含 10 张图片的 HTML 页面，用持久连接比挨个连接更快，管线化又比持久连接更快，**请求数越多，时间差越明显**。

### 2.6 HTTP 方法：告诉服务器你想做什么

方法（method）是请求行开头的那个词，作用是**指定请求的资源按期望产生某种行为**。方法名区分大小写，必须用大写字母。

**表 2-7　HTTP 方法一览（原书表 2-1，第 41 页）**

| 方法 | 说明 | 协议版本 | 幂等 | 典型用途 |
| --- | --- | --- | --- | --- |
| `GET` | 获取资源。资源是文本就原样返回，是 CGI 之类的程序就返回执行结果 | 1.0 / 1.1 | 是 | 打开页面、读接口 |
| `POST` | 传输实体主体。主要目的不是获取响应主体内容 | 1.0 / 1.1 | 否 | 提交表单、创建资源 |
| `PUT` | 传输文件，把请求主体里的内容保存到 URI 指定位置 | 1.0 / 1.1 | 是 | 上传覆盖（REST） |
| `HEAD` | 和 GET 一样，但不返回报文主体，只返回首部 | 1.0 / 1.1 | 是 | 确认资源是否存在/更新 |
| `DELETE` | 删除文件，与 PUT 相反，按请求 URI 删除指定资源 | 1.0 / 1.1 | 是 | 删除资源（REST） |
| `OPTIONS` | 询问针对请求 URI 指定资源支持的方法 | 1.1 | 是 | 跨域预检（CORS） |
| `TRACE` | 让服务器把之前的请求通信环回给客户端，用于追踪路径 | 1.1 | 是 | 诊断（少用） |
| `CONNECT` | 与代理服务器建立隧道，用隧道协议进行 TCP 通信 | 1.1 | 否 | HTTPS 代理隧道 |
| `PATCH` | 「书外延伸」对资源做局部更新 | RFC5789 | 否 | 只改某几个字段 |

补充两点原书提到的限制：**PUT 与 DELETE 本身不带验证机制**，任何人都可以上传或删除文件，存在安全问题，因此一般的 Web 网站不使用它们；只有在配合应用层验证机制，或按 REST 标准设计的架构里才可能开放。`LINK` 和 `UNLINK` 已被 HTTP/1.1 废弃。

#### GET 与 POST 的区别（面试高频）

**表 2-8　GET 与 POST 的对比**

| 维度 | GET | POST |
| --- | --- | --- |
| 语义 | 获取资源（读） | 提交数据（写） |
| 参数位置 | 拼在 URL 的查询字符串里 | 放在报文主体里 |
| 能否收藏 / 分享 | 可以，URL 自带全部参数 | 不可以，参数在请求体里 |
| 是否被浏览器缓存 | 通常会被缓存 | 默认不缓存 |
| 是否留在历史记录 | 会 | 不会（地址栏不变） |
| 长度限制 | 受 URL 长度限制（约 2KB） | 理论上无限制，受服务器配置约束 |
| 幂等 / 安全 | 幂等、只读，重复请求无副作用 | 非幂等，重复提交可能产生多份数据 |

> ⚠️ **别把区别记成“GET 参数在 URL、POST 在 body”**　那只是表象。真正的区别是**语义**：GET 是“我要看”，POST 是“我要交”。正因语义不同，浏览器才敢缓存 GET、才敢让你收藏地址、表单刷新时才会提示重复提交。

> 💡 **本章小结**　① TCP/IP 分层，HTTP 在应用层；② 每下一层封装一个首部；③ DNS 换地址、TCP 保可靠、IP 找路由；④ 1.1 用持久连接 + 管线化缓解请求数；⑤ 方法的本质是语义。

## 03 核心概念逐个击破

> 这一章是手册，不必一次读完。每个概念都按「一句话定义 → 结构拆解 → 易错点」来讲，目的是让你在遇到 `Host`、`ETag`、`304`、`payload` 这些词时，能立刻说出它在哪里、干什么用。

### 3.1 URI 与 URL

与 URI（统一资源标识符）相比，我们更熟悉 URL（Uniform Resource Locator，统一资源定位符）——它正是使用浏览器访问 Web 页面时需要输入的网页地址。但两者的关系必须先理清：

**表 3-1　URI 与 URL 的关系**

|  | URI | URL |
| --- | --- | --- |
| 全称 | Uniform Resource Identifier | Uniform Resource Locator |
| 中文 | 统一资源标识符 | 统一资源定位符 |
| 回答的问题 | **这个东西是什么**（用字符串标识某个资源） | **这个东西在哪里**（资源在互联网上的位置） |
| 外延 | 更大，是父集 | 更小，**URL 是 URI 的子集** |

URI 的三个词可以拆开理解：**Uniform** 规定统一的格式，方便处理多种不同类型的资源，而不必根据上下文去识别访问方式；**Resource** 的定义是“可标识的任何东西”，文档、图像、一项服务（比如当天的天气预报）都算；**Identifier** 表示可标识的对象，也叫标识符。

换句话说，**URI 就是由某个协议方案表示的资源的定位标识符**。协议方案就是访问资源时使用的协议类型名称：用 HTTP 时是 `http`，此外还有 `ftp`、`mailto`、`telnet`、`file` 等 30 种左右，由 IANA 统一管理。

#### 3.1.1 绝对 URI 的七个组成部分

把下面这个典型的绝对 URI 拆开，就是全部零件：

```text
http://user:pass@www.example.jp:80/dir/index.htm?uid=1#ch1

  http:     协议方案名
  user:pass 登录信息（可省略）
  www.example.jp        服务器地址
  :80       服务器端口号（可省略）
  /dir/index.htm        带层次的文件路径
  ?uid=1    查询字符串
  #ch1      片段标识符（不会发给服务器）
```

**表 3-2　绝对 URI 的组成部分（原书第 27 页）**

| 组成部分 | 示例 | 说明 | 可省略 |
| --- | --- | --- | --- |
| 协议方案名 | `http:` | 访问资源时要指定的协议类型，不区分大小写，末尾带冒号；也可用 `data:`、`javascript:` 这类方案 | 否 |
| 登录信息（认证） | `user:pass` | 从服务器获取资源时必要的用户名和密码 | 是 |
| 服务器地址 | `www.example.jp` | 可以是 DNS 可解析的名称、IPv4 地址，或 `[0:0:0:0:0:0:0:1]` 这样带方括号的 IPv6 地址 | 否 |
| 服务器端口号 | `:80` | 指定连接的网络端口号，省略则用协议的默认端口 | 是 |
| 带层次的文件路径 | `/dir/index.htm` | 指定服务器上的文件路径来定位特指的资源，与 UNIX 的目录结构相似 | 是 |
| 查询字符串 | `?uid=1` | 针对已指定的文件路径内的资源，传入任意参数 | 是 |
| 片段标识符 | `#ch1` | 标记已获取资源中的子资源（文档内的某个位置）；RFC 未明确规定其使用方法 | 是 |

> ⚠️ **`#` 后面的内容不会发给服务器**　片段标识符（fragment）只在浏览器内部使用 —— 浏览器用它定位到页面里的某个锚点，**不会把它放进 HTTP 请求的 URI 里**。所以服务端永远收不到 `#ch1`，需要靠 JS 读取 `location.hash`。这是一个非常常见的误解。

另一种是**相对 URL**，指从浏览器中基本 URI 处指定的 URL，形如 `/image/logo.gif`。浏览器会把它和当前页面的 URL 拼成绝对 URL 再去请求。

> 可见 URL 是 URI 的子集。本书接下来的章节中会频繁出现 URI 这个术语，在充分理解的基础上，也可用 URL 替换 URI。
>
> —— 《图解HTTP》第 26 页

### 3.2 IP、端口、域名、MAC：四个容易混淆的地址

这四个概念经常被混着说，其实它们解决的是完全不同的问题。用一个寄快递的类比就能分清：

**表 3-3　四个地址概念的分工**

| 概念 | 是什么 | 例子 | 谁在用 / 特点 |
| --- | --- | --- | --- |
| IP 地址 | 节点在网络中被分配到的逻辑地址 | `192.0.2.1`、`2001:db8::7` | 网络层用来找机器；**可以变换**（换网络就换地址） |
| MAC 地址 | 网卡所属的固定物理地址 | `00:1A:2B:3C:4D:5E` | 链路层用来在同一局域网内传输；**基本不会更改** |
| 域名 | 给人看的、便于记忆的主机名 | `www.hackr.jp` | 用户使用；需经 DNS 解析成 IP 才能通信 |
| 端口号 | 一台机器上某个进程的门牌号 | `80`（HTTP）、`443`（HTTPS） | 传输层用来区分不同服务；同一 IP 上可跑多个服务 |

还有一个常见混淆：**IP 是一种协议的名称，不是地址**。说“IP 是网际协议”时指协议，说“IP 地址”时指那个数字。原书特意提醒过这一点。

### 3.3 HTTP 报文的结构

用于 HTTP 协议交互的信息被称为 **HTTP 报文**。请求端的叫**请求报文**，响应端的叫**响应报文**。报文本身是由多行（用 CR+LF 作换行符）数据构成的字符串文本。

结构上大致分为**报文首部**和**报文主体**两块，两者由最初出现的**空行**（CR+LF）划分。通常，并不一定要有报文主体。

```text
HTTP 报文
  |-- 报文首部
  |     |-- 起始行：请求行（方法 + URI + 版本）或状态行（版本 + 状态码 + 原因短语）
  |     `-- 首部字段：若干行「名字: 值」
  |-- 空行（CR+LF）：分隔符，必须有
  `-- 报文主体（可无）：真正要传的数据
```

**表 3-4　请求报文与响应报文的结构对照（原书第 49–51 页）**

| 位置 | 请求报文 | 响应报文 |
| --- | --- | --- |
| 起始行 | **请求行**：方法 + 请求 URI + HTTP 版本<br>`GET /index.htm HTTP/1.1` | **状态行**：HTTP 版本 + 状态码 + 原因短语<br>`HTTP/1.1 200 OK` |
| 首部 | 请求首部字段、通用首部字段、实体首部字段 | 响应首部字段、通用首部字段、实体首部字段 |
| 空行 | 一个 CR+LF | 一个 CR+LF |
| 主体 | 内容实体（GET 通常为空，POST 放表单数据） | 资源实体的主体（HTML、图片二进制等） |
| 其他 | 还可能包含 RFC 未定义的首部（如 `Cookie`） | 还可能包含 RFC 未定义的首部（如 `Set-Cookie`） |

首部一共有四类：**通用首部**（请求响应都会用）、**请求首部**（客户端发）、**响应首部**（服务器发）、**实体首部**（针对实体部分）。这四类分别在 3.5–3.7 节展开。

### 3.4 “负载”（payload）到底指什么

你在抓包工具或接口文档里看到的 payload，对应的就是原书里的**实体主体**（entity body）——请求或响应中真正承载数据的那一段。但这里有三层概念必须分清，否则很容易说错。

#### 3.4.1 报文主体、实体主体、实体首部

> 报文（message）是 HTTP 通信中的基本单位，由 8 位组字节流组成；实体（entity）作为请求或响应的有效载荷数据被传输，其内容由实体首部和实体主体组成。
>
> —— 《图解HTTP》第 51 页

**表 3-5　报文与实体的区别**

| 概念 | 是什么 | 例子 |
| --- | --- | --- |
| 报文 message | HTTP 通信的基本单位，就是一整条请求或响应 | 整个 `GET ...` 或 `HTTP/1.1 200 ...` 文本 |
| 报文主体 | 报文中空行之后的那一段字节流 | `{"name":"张三"}` |
| 实体 entity | 作为有效载荷被传输的数据，= 实体首部 + 实体主体 | `Content-Type: application/json` + 上面那串 JSON |
| 实体主体 | 实体中真正的内容部分，也就是通常说的 payload | `{"name":"张三"}` |
| 实体首部 | 描述实体的首部字段 | `Content-Type`、`Content-Length`、`Content-Encoding` |

关键结论：**通常报文主体 = 实体主体**。只有当传输中进行了编码操作，实体主体的内容发生变化时，两者才会产生差异 —— 比如 gzip 压缩、分块传输。这就是为什么抓包看到的“报文主体”可能是一堆乱码，而接口文档里写的 payload 是明文 JSON。

#### 3.4.2 长度怎么表示：Content-Length 与分块传输

服务器要告诉客户端“主体有多长”，有两种方式，二者**互斥**：

**表 3-6　两种表示主体长度的方式**

| 方式 | 首部 | 适用场景 | 注意 |
| --- | --- | --- | --- |
| 定长 | `Content-Length: 15000` | 主体长度已知 | 对实体主体进行内容编码传输时，**不能再用** `Content-Length` |
| 分块 | `Transfer-Encoding: chunked` | 主体长度未知，边生成边发送（如动态页面、大文件流） | 每块用十六进制标记大小，最后以 `0(CR+LF)` 结束 |

```http
HTTP/1.1 200 OK
Content-Type: text/javascript; charset=utf-8
Transfer-Encoding: chunked

cf0                     ← 十六进制 cf0 = 十进制 3312，表示本块 3312 字节
...3312 字节数据...
392                     ← 十六进制 392 = 十进制 914
...914 字节数据...
0                       ← 长度为 0，表示结束
```

分块传输的价值在于：**服务器不必等整个响应生成完才发第一个字节**。浏览器可以边收边渲染，大文件下载也能逐步显示进度。

#### 3.4.3 内容编码：把主体压缩后再传

HTTP 有一种称为**内容编码**的功能：指明应用在实体内容上的编码格式，并保持实体信息原样压缩。编码后的实体由客户端接收并负责解码。

**表 3-7　四种常见内容编码**

| 编码 | 说明 |
| --- | --- |
| `gzip` | 由 gzip（GNU zip）生成的编码格式（RFC1952），采用 LZ77 算法及 32 位 CRC 校验 |
| `compress` | 由 UNIX 的 compress 程序生成的编码格式，采用 LZW 算法 |
| `deflate` | 组合使用 zlib 格式（RFC1950）与 deflate 压缩算法（RFC1951） |
| `identity` | 不执行压缩的默认编码格式 |

```http
请求：客户端声明自己能解哪些编码
Accept-Encoding: gzip, deflate

响应：服务器说明用了哪种编码
Content-Encoding: gzip
Content-Type: text/html; charset=UTF-8
```

#### 3.4.4 多部分对象集合：一次发多种数据

发送邮件时可以在正文里写入文字并添加多份附件，靠的是 MIME 机制。HTTP 也采纳了其中的**多部分对象集合**（Multipart），让一份报文主体内可以含有多个不同类型的实体。最典型的使用场景是**表单文件上传**。

**表 3-8　两种多部分对象集合**

| 类型 | 使用场景 |
| --- | --- |
| `multipart/form-data` | Web 表单文件上传时使用 |
| `multipart/byteranges` | 状态码 206 的响应中，报文包含多个范围的内容时使用 |

```http
Content-Type: multipart/form-data; boundary=AaB03x

--AaB03x
Content-Disposition: form-data; name="field1"

Joe Blow
--AaB03x
Content-Disposition: form-data; name="pics"; filename="file1.txt"
Content-Type: text/plain

...（file1.txt 的数据）...
--AaB03x--
```

用 `boundary` 字符串划分各个实体：每个部分的起始行之前插入 `--` 标记，最后再加 `--` 作为结束。每个部分内部都可以有自己的首部，甚至可以嵌套多部分对象集合。

#### 3.4.5 范围请求：只取一部分

下载大文件时如果网络中断，从前只能从头再来。**范围请求**（Range Request）允许指定下载的实体范围，从而实现断点续传。

```http
Range: bytes=5001-10000      ← 第 5001 到 10000 字节
Range: bytes=5001-           ← 从 5001 字节之后全部
Range: bytes=-3000, 5000-7000 ← 多重范围：从头到 3000，以及 5000~7000
```

服务器能处理时返回 `206 Partial Content`，并用 `Content-Range` 标明返回的是哪一段；多重范围则返回 `multipart/byteranges`。**无法处理时，返回 200 OK 和完整的实体内容**。

#### 3.4.6 内容协商：同一 URI，不同内容

同一个 Web 网站可能存在多份内容相同但语言不同的页面。浏览器访问同一 URI 时能显示对应语言的版本，这个机制称为**内容协商**（Content Negotiation）—— 客户端和服务器就响应的资源内容进行交涉，然后提供最合适的资源。

判断基准就是请求里的这几个首部字段：`Accept`、`Accept-Charset`、`Accept-Encoding`、`Accept-Language`、`Content-Language`。协商有三种类型：**服务器驱动协商**（服务器按请求首部自动判断）、**客户端驱动协商**（用户从列表里手动选，或 JS 自动切换 PC/手机版）、**透明协商**（两者结合）。

### 3.5 请求头（请求首部字段）

请求首部字段是从客户端往服务器端发送请求报文时使用的字段，用于补充请求的附加信息、客户端信息、对响应内容相关的优先级等内容。下表是 HTTP/1.1 定义的 19 个请求首部字段。

**表 3-9　请求首部字段速查（原书表 6-2，第 83 页）**

| 字段 | 作用 | 示例 / 备注 |
| --- | --- | --- |
| `Accept` | 通知服务器用户代理能够处理的媒体类型及相对优先级 | `text/html,application/xml;q=0.9,*/*;q=0.8`；q 为权重 0~1 |
| `Accept-Charset` | 通知服务器支持的字符集及优先顺序 | `iso-8859-5, unicode-1-1;q=0.8` |
| `Accept-Encoding` | 告知支持的内容编码及优先级 | `gzip, deflate` |
| `Accept-Language` | 告知能够处理的自然语言集及优先级 | `zh-cn,zh;q=0.7,en-us;q=0.3` |
| `Authorization` | 告知服务器用户代理的认证信息 | `Basic dWVub3NlbjpwYXNzd29yZA==`；通常在收到 401 后才发 |
| `Expect` | 告知服务器期望出现的某种特定行为 | `100-continue`；服务器无法理解时返回 417 |
| `From` | 告知使用用户代理的用户的电子邮件地址 | 多用于爬虫，方便联系负责人 |
| `Host` | 告知请求的资源所处的互联网主机名和端口号 | **HTTP/1.1 中唯一必须包含的请求首部**；虚拟主机靠它区分 |
| `If-Match` | 条件请求：ETag 与字段值一致时才执行 | 不一致返回 `412 Precondition Failed`；可用 `*` 匹配任意存在资源 |
| `If-Modified-Since` | 条件请求：资源在该时间后更新过才处理 | 未更新则返回 `304 Not Modified` |
| `If-None-Match` | 条件请求：ETag 与字段值**不一致**时才处理 | 与 `If-Match` 作用相反；GET/HEAD 中用于取最新资源 |
| `If-Range` | 条件请求：ETag/时间一致时按范围请求处理，否则返回全体 | 避免两次请求的浪费 |
| `If-Unmodified-Since` | 条件请求：该时间后未更新才处理 | 与 `If-Modified-Since` 相反；否则返回 412 |
| `Max-Forwards` | 以十进制整数指定可经过的服务器最大数目 | 每转发一次减 1，为 0 时直接返回响应；配合 TRACE/OPTIONS 排查 |
| `Proxy-Authorization` | 告知代理服务器认证所需的信息 | 认证发生在客户端与代理之间 |
| `Range` | 只获取部分资源 | `bytes=5001-10000`；成功返回 206 |
| `Referer` | 告知服务器请求的原始资源的 URI | 从哪个页面点过来的；含敏感信息时可能不发送 |
| `TE` | 告知能处理的传输编码方式及优先级 | `gzip, deflate;q=0.5`；也可指定 `trailers` |
| `User-Agent` | 传达创建请求的浏览器和用户代理名称等信息 | `Mozilla/5.0 (...) Firefox/13.0.1`；爬虫可能附带邮箱 |

> ⚠️ **Host 为什么是“唯一必需”**　请求发到服务器时，主机名会被替换成 IP 地址。若同一个 IP 下部署了多个域名（虚拟主机），服务器就无法判断你到底要访问哪个站点。`Host` 就是用来补上这个信息的 —— 这也是它成为 HTTP/1.1 中唯一必需请求首部的原因。

### 3.6 响应头（响应首部字段）

响应首部字段是由服务器端向客户端返回响应报文时使用的字段，用于补充响应的附加信息、服务器信息，以及对客户端的附加要求等信息。

**表 3-10　响应首部字段速查（原书表 6-3，第 83 页）**

| 字段 | 作用 | 示例 / 备注 |
| --- | --- | --- |
| `Accept-Ranges` | 告知客户端服务器是否能处理范围请求 | `bytes` 表示可以，`none` 表示不可以 |
| `Age` | 告知客户端源服务器在多久前创建了响应 | 单位秒；缓存服务器创建响应时必须加上 |
| `ETag` | 告知客户端实体标识，是资源的唯一性字符串标识 | `"82e222..."`；资源更新时 ETag 也要更新 |
| `Location` | 将响应接收方引导至某个与请求 URI 位置不同的资源 | 配合 3xx 重定向使用；浏览器会强制跳转 |
| `Proxy-Authenticate` | 把由代理服务器所要求的认证信息发送给客户端 | 认证发生在客户端与代理之间 |
| `Retry-After` | 告知客户端应该在多久之后再次发送请求 | 配合 503 或 3xx 使用；可给秒数或具体时间 |
| `Server` | 告知客户端当前服务器上安装的 HTTP 服务器应用程序信息 | `Apache/2.2.17 (Unix)` |
| `Vary` | 对缓存进行控制：指定首部字段不同时须重新获取资源 | `Vary: Accept-Language` |
| `WWW-Authenticate` | 告知客户端适用于请求 URI 指定资源的认证方案 | `Basic realm="..."`；401 响应中必定带有 |

`ETag` 还有强弱之分：**强 ETag** 不论实体发生多么细微的变化都会改变值；**弱 ETag** 只在资源发生根本改变时才变，值的最前面会加 `W/`，如 `ETag: W/"usagi-1234"`。

### 3.7 通用首部与实体首部

**通用首部字段**是请求报文和响应报文双方都会使用的首部。

**表 3-11　通用首部字段（原书表 6-1，第 82 页）**

| 字段 | 作用 | 要点 |
| --- | --- | --- |
| `Cache-Control` | 控制缓存的行为 | `no-cache`（不缓存过期资源，需再验证）、`no-store`（完全不缓存）、`max-age`、`public`、`private`、`must-revalidate` |
| `Connection` | 控制不再转发给代理的首部字段；管理持久连接 | `Connection: close` 关闭连接；`Keep-Alive` 维持旧版本长连接 |
| `Date` | 表明创建 HTTP 报文的日期和时间 | RFC1123 格式，如 `Tue, 03 Jul 2012 04:40:59 GMT` |
| `Pragma` | HTTP/1.1 之前的历史遗留字段，仅为向后兼容 | `Pragma: no-cache`，常与 `Cache-Control` 同时发 |
| `Trailer` | 事先说明在报文主体后记录了哪些首部字段 | 用于分块传输编码时 |
| `Transfer-Encoding` | 规定传输报文主体时采用的编码方式 | HTTP/1.1 中仅对分块传输编码有效 |
| `Upgrade` | 检测 HTTP 及其他协议是否可使用更高版本通信 | 需配合 `Connection: Upgrade`；服务器可回 101 |
| `Via` | 追踪客户端与服务器之间的请求和响应报文的传输路径 | 每经过一个代理就追加一条；也能避免请求回环 |
| `Warning` | 告知用户一些与缓存相关的问题的警告 | 如 `110 Response is stale` |

**实体首部字段**是包含在请求报文和响应报文中的实体部分所使用的首部，用于补充内容的更新时间等与实体相关的信息。

**表 3-12　实体首部字段（原书表 6-4，第 84 页）**

| 字段 | 作用 | 要点 |
| --- | --- | --- |
| `Allow` | 通知客户端能够支持 Request-URI 指定资源的所有 HTTP 方法 | 服务器返回 405 时，会同时把所有支持的方法写入 `Allow` |
| `Content-Encoding` | 告知服务器对实体主体选用的内容编码方式 | `gzip`、`compress`、`deflate`、`identity` |
| `Content-Language` | 告知实体主体使用的自然语言 | `zh-CN` |
| `Content-Length` | 表明实体主体部分的大小（字节） | 编码传输时不能使用 |
| `Content-Location` | 给出与报文主体部分相对应的 URI | 与 `Location` 不同，它表示报文主体对应的 URI |
| `Content-MD5` | 实体主体的报文摘要，检查完整性 | MD5 后 Base64 编码；**无法防恶意篡改**（摘要可被一并改掉） |
| `Content-Range` | 告知作为响应返回的实体哪个部分符合范围请求 | `bytes 5001-10000/10000` |
| `Content-Type` | 说明实体主体内对象的媒体类型 | `text/html; charset=UTF-8` |
| `Expires` | 将资源失效的日期告知客户端 | 超过该时间缓存服务器会转向源服务器；有 `max-age` 时优先 `max-age` |
| `Last-Modified` | 指明资源最终修改的时间 | `If-Modified-Since` 的比对对象 |

### 3.8 Cookie 相关首部

Cookie 没有被编入 HTTP/1.1 的 RFC2616，但在 Web 上应用极广。它只有两个首部字段：响应中的 `Set-Cookie`（下发）和请求中的 `Cookie`（回传）。

**表 3-13　Set-Cookie 的字段值（原书表 6-9，第 130 页）**

| 属性 | 说明 | 安全提示 |
| --- | --- | --- |
| `NAME=VALUE` | 赋予 Cookie 的名称和值（必需项） | 值本身通常只是一个无意义的句柄 |
| `expires=DATE` | Cookie 的有效期；省略则默认为浏览器关闭前为止 | 服务器无法显式删除 Cookie，只能覆盖成已过期的值 |
| `path=PATH` | 将服务器上的文件目录作为 Cookie 的适用对象 | 可被绕过，**不宜当作安全机制** |
| `domain=域名` | 作为 Cookie 适用对象的域名；省略则为创建 Cookie 的服务器域名 | 会匹配结尾；除必要外不指定更安全 |
| `Secure` | 仅在 HTTPS 安全通信时才会发送 Cookie | HTTP 站点将不会带上它 |
| `HttpOnly` | 限制 Cookie 不能被 JavaScript 访问 | 防 XSS 窃取 Cookie 的主要手段 |

```http
Set-Cookie: status=enable; expires=Tue, 05 Jul 2011 07:26:31 GMT;
            path=/; domain=.hackr.jp; Secure; HttpOnly

Cookie: status=enable
```

### 3.9 首部的两种分类：端到端与逐跳

从**缓存代理是否转发**的角度，HTTP 首部又可分为两类：**端到端首部**会转发给请求 / 响应对应的最终接收目标，且必须保存在缓存生成的响应中；**逐跳首部**只对单次转发有效，经过缓存或代理后就不再转发。

HTTP/1.1 中共有 **8 个逐跳首部**，除此之外全部属于端到端首部：

| 逐跳首部（8 个） |
| --- |
| `Connection` · `Keep-Alive` · `Proxy-Authenticate` · `Proxy-Authorization`<br>`Trailer` · `TE` · `Transfer-Encoding` · `Upgrade` |

如果要在 HTTP/1.1 及之后版本中使用逐跳首部，需要提供 `Connection` 首部字段来声明。理解了这一点，就能明白为什么跨代理的链路里 `Connection` 会被“吃掉”。

### 3.10 状态码：服务器的回答摘要

状态码的职责是当客户端向服务器端发送请求时，**描述返回的请求结果**。借助状态码，用户可以知道服务器端是正常处理了请求，还是出现了错误。

状态码如 `200 OK`，由 **3 位数字 + 原因短语**组成。数字的第一位指定了响应类别，后两位无分类。只要遵守类别定义，即使服务器自行创建状态码也没问题。

**表 3-14　状态码的 5 个类别（原书表 4-1，第 60 页）**

| 类别 | 原因短语 | 含义 | 记忆 |
| --- | --- | --- | --- |
| **1XX** | Informational | 接收的请求正在处理 | 信息 —— 还在处理，请稍等 |
| **2XX** | Success | 请求正常处理完毕 | 成功 |
| **3XX** | Redirection | 需要进行附加操作以完成请求 | 重定向 —— 去别处拿 |
| **4XX** | Client Error | 服务器无法处理请求 | **你（客户端）错了** |
| **5XX** | Server Error | 服务器处理请求出错 | **我（服务器）错了** |

RFC2616 上记录的状态码就有 40 种，加上 WebDAV 与附加状态码等扩展可达 60 余种。但实际上**经常使用的大概只有 14 种**。

**表 3-15　最常用的 14 个状态码（原书第 61–68 页）**

| 状态码 | 原因短语 | 含义 | 典型场景 |
| --- | --- | --- | --- |
| `200` | OK | 请求在服务器端被正常处理 | GET 成功返回页面；HEAD 时只回首部 |
| `204` | No Content | 请求已成功处理，但响应中不含实体主体，也不允许返回 | 只需客户端上报信息、无需返回新内容 |
| `206` | Partial Content | 客户端进行了范围请求，服务器成功执行了这部分 GET | 断点续传、视频拖动进度条 |
| `301` | Moved Permanently | **永久性重定向**：资源已被分配新的 URI，以后应使用新 URI | 换域名、URL 规范化（如末尾补斜杠） |
| `302` | Found | **临时性重定向**：资源已被分配新的 URI，希望本次用新 URI 访问 | 登录后临时跳转；书签不会更新 |
| `303` | See Other | 资源存在另一个 URI，**应使用 GET 方法**定向获取 | POST 处理后跳转到结果页 |
| `304` | Not Modified | 附带条件的请求未满足条件；不包含响应主体 | 缓存仍然有效，省一次传输 |
| `307` | Temporary Redirect | 临时重定向，**不会把 POST 变成 GET** | 需要保持原方法和主体的临时跳转 |
| `400` | Bad Request | 请求报文中存在语法错误 | 参数格式错误 |
| `401` | Unauthorized | 请求需要 HTTP 认证信息；之前已请求过则表示认证失败 | 响应必带 `WWW-Authenticate`；浏览器弹登录框 |
| `403` | Forbidden | 对请求资源的访问被服务器拒绝 | 没有文件系统权限、来源 IP 被拒 |
| `404` | Not Found | 服务器上无法找到请求的资源 | URL 写错、资源已删除；也可用于拒绝且不想说明理由 |
| `500` | Internal Server Error | 服务器端在执行请求时发生了错误 | Web 应用 bug、临时故障 |
| `503` | Service Unavailable | 服务器暂时处于超负载或正在停机维护 | 最好同时返回 `Retry-After` |

#### 3.10.1 六个必须记牢的细节

**① 301 与 302 的区别，在于“永久”还是“临时”。** 301 时，已保存的书签应该按 `Location` 提示的 URI 重新保存；302 则不应该更新书签，因为将来还可能变。

**② 302 在现实中经常被当成 303 用。** 标准禁止把 POST 改成 GET，但几乎所有浏览器在收到 301、302、303 时都会把 POST 改成 GET，并删除请求报文内的主体后自动再发一次。所以 303 才是“明确表示用 GET”的那个。

**③ 304 虽然被划在 3XX，但和重定向没有关系。** 它表示“你手里的缓存还能用”，响应里不包含任何主体。附带条件的请求指 GET 请求中带有 `If-Match`、`If-Modified-Since`、`If-None-Match`、`If-Range`、`If-Unmodified-Since` 中任一首部。

**④ 401 和 403 不是一回事。** 401 是“你还没证明你是谁”（需要认证，响应必带 `WWW-Authenticate`）；403 是“我知道你是谁，但你不能看”（拒绝访问）。

**⑤ 200 不代表业务成功。** 原书专门提醒：不少返回的状态码响应都是错误的，但用户可能察觉不到 —— Web 应用程序内部发生错误，状态码依然返回 `200 OK`，这种情况也经常遇到。看接口是否成功，不能只看 HTTP 状态码，还要看响应体里的业务码。

**⑥ 状态码是可以自己造的。** 只要守住“首位定类别”的规矩，服务器可以自定义状态码；扩展状态码还有 `405`（方法不允许）、`412`（前置条件失败）、`417`（期望失败）、`504`（网关超时）等。

> 💡 **本章小结**　① **URI 是标识，URL 是定位**，URL 是 URI 的子集；② 报文 = 起始行 + 首部 + 空行 + 主体，**通常报文主体 = 实体主体**；③ payload 指实体主体，长度靠 `Content-Length` 或分块传输表示；④ 首部分四类（通用 / 请求 / 响应 / 实体），另可按端到端 / 逐跳分；⑤ 状态码看**首位定类别**，14 个常用码足够应付 95% 的场景。

## 04 串起来：三个场景各走一遍

> 知识只有连成线才有用。这一章把前面所有零件装回去，用三个最常见的场景跑一遍：第一次访问、带着缓存再访问、提交登录表单。建议对照开发者工具的 Network 面板逐行看。

### 4.1 第一次访问一个网站

场景：在浏览器输入 `http://hackr.jp/index.html`，本地没有任何缓存。

#### ① 解析 URL

协议 `http`、主机 `hackr.jp`、端口省略（默认 80）、路径 `/index.html`、无查询字符串。

#### ② DNS 解析

浏览器先查自身缓存、系统 hosts、本地 DNS 缓存，都没有就问 DNS 服务器，最终拿到 IP，比如 `192.0.2.1`。**从这一刻起，后续所有通信都只用 IP，不再出现域名。**

#### ③ TCP 三次握手

```text
客户端 ──── SYN (seq=x) ───────────────────→ 服务器
客户端 ←─── SYN + ACK (seq=y, ack=x+1) ──── 服务器
客户端 ──── ACK (ack=y+1) ───────────────→ 服务器
                    【连接建立】
```

#### ④ 发送请求报文

```http
GET /index.html HTTP/1.1
Host: hackr.jp
User-Agent: Mozilla/5.0 (Windows NT 6.1; WOW64; rv:13.0) Gecko/20100101 Firefox/13.0
Accept: text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8
Accept-Language: ja,en-us;q=0.7,en;q=0.3
Accept-Encoding: gzip, deflate
Connection: keep-alive

（GET 没有请求体）
```

#### ⑤ 服务器处理

Web 服务器（如 Apache、Nginx）根据 `Host` 判断是哪个虚拟主机，根据路径找到文件或转发给后端程序，生成响应内容。

#### ⑥ 返回响应报文

```http
HTTP/1.1 200 OK
Date: Tue, 10 Jul 2012 06:50:15 GMT
Server: Apache
Content-Length: 362
Content-Type: text/html
Connection: keep-alive

<html>
  <head><title>...</title></head>
  <body>...</body>
</html>
```

#### ⑦ 浏览器解析与再请求

解析 HTML 时遇到 `<img src="logo.png">`，浏览器再发一个 GET 拿图片。因为用了持久连接，**这些请求复用同一条 TCP 连接**，不再重复握手。这就是 1.1 相对 1.0 最大的提速点。

> 💡 **观察练习**　打开任意网站，按 F12 → Network，勾选 “Disable cache” 后刷新。你会看到：第一条是 `document` 类型（HTML），后面跟着几十条图片 / CSS / JS 请求，最后一条 `Connection ID` 往往和前面相同 —— 这就是持久连接在起作用。

### 4.2 再次访问同一个页面（命中缓存 / 304）

第二次访问同一页面时，浏览器手里已经有副本。它不会直接信任，而是**先问服务器“还能用吗”**。

```http
GET /index.html HTTP/1.1
Host: hackr.jp
If-None-Match: "45bae1-16a-46d776ac"        ← 上次响应给的 ETag
If-Modified-Since: Fri, 31 Aug 2007 02:02:20 GMT

HTTP/1.1 304 Not Modified
Date: Thu, 07 Jun 2012 07:21:36 GMT
ETag: "45bae1-16a-46d776ac"

（304 没有响应体 —— 浏览器直接用本地副本）
```

**表 4-1　条件请求的四种结果**

| 情况 | 服务器的判断 | 返回 | 客户端行为 |
| --- | --- | --- | --- |
| ETag 一致 / 资源未修改 | 缓存有效 | `304 Not Modified`（无主体） | 直接用本地副本，省掉传输 |
| ETag 不一致 / 资源已更新 | 缓存失效 | `200 OK` + 新内容 | 替换本地副本并渲染 |
| 缓存已过期且不允许复用 | 必须重取 | `200 OK` + 完整内容 | 重新下载 |
| 条件不满足（如 If-Match 失败） | 前置条件失败 | `412 Precondition Failed` | 按业务逻辑处理 |

这里的 `ETag` 和 `Last-Modified` 就是**缓存校验器**，`If-None-Match` 和 `If-Modified-Since` 是**校验请求**。这就是 1.4 节提到的“缓存要判断副本是否过期”的具体实现。

### 4.3 提交登录表单（POST + Cookie + 重定向）

场景：在登录页输入用户名密码，点击“登录”。这一次不是 GET，而是 POST；服务器也不直接返回页面，而是让浏览器“去别处”。

#### 第一跳：提交表单

```http
POST /login HTTP/1.1
Host: hackr.jp
Content-Type: application/x-www-form-urlencoded
Content-Length: 32

username=alice&password=secret123
```

#### 第二跳：服务器下发 Cookie 并要求跳转

```http
HTTP/1.1 302 Found
Location: http://hackr.jp/mypage
Set-Cookie: sid=1342077140226724; path=/; HttpOnly; Secure
Content-Length: 0

（302 通常没有响应体）
```

注意三件事：**状态码 302 表示临时跳转**，`Location` 给出目标地址，`Set-Cookie` 下发会话凭证。浏览器收到后自动再发一次 GET 到 `/mypage`，这次请求就带上了 Cookie。

#### 第三跳：带着身份访问

```http
GET /mypage HTTP/1.1
Host: hackr.jp
Cookie: sid=1342077140226724

HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8

<html>欢迎回来，alice</html>
```

到这里，三个关键机制全部出场：**POST 传负载**、**302 + Location 重定向**、**Set-Cookie / Cookie 维持状态**。而 `HttpOnly` 和 `Secure` 两个属性，分别用来防 XSS 窃取和防明文传输泄露。

> ⚠️ **为什么登录后要用 302 而不是直接返回页面**　直接返回页面会导致“刷新即重复提交表单”的问题：用户按 F5，浏览器会再发一次 POST，可能重复下单、重复登录。**PRG 模式**（Post/Redirect/Get）用 302 把 POST 变成 GET，刷新就只是重新 GET 一次结果页。这是 Web 开发里最基本的习惯之一。

#### 动手练一练

1. 在终端执行 `curl -i http://example.com`，只看响应首部；再用 `curl -v` 看全过程，注意 `>` 是发出的、`<` 是收到的。
2. 用 `curl -L` 访问一个会跳转的短链接，观察 301/302 与 `Location`。
3. 在浏览器里强制刷新（Ctrl+F5）和普通刷新各一次，对比请求首部里 `Cache-Control`、`If-None-Match` 的差别。

> 考前翻一翻、写代码卡住时查一查。四张卡：流程、状态码、首部、术语。

### 5.1 一页纸流程卡

```text
① URL  ── 拆成 协议 / 主机 / 端口 / 路径 / 查询
② DNS  ── 域名 → IP（应用层，UDP 53）
③ TCP  ── SYN → SYN+ACK → ACK，连接建立（传输层）
④ 请求 ── 请求行 + 首部 + 空行 + 主体

⑥ 响应 ── 状态行 + 首部 + 空行 + 主体
⑦ 渲染 ── 解析 HTML → 继续发子资源请求 → 绘制

贯穿全过程的三个开关：
  · 身份    Cookie / Set-Cookie
  · 缓存    Cache-Control / ETag / Last-Modified / 304
  · 连接    Connection: keep-alive / close
```

| 持久连接 | persistent connection / keep-alive | 一条 TCP 连接跑多次请求 |
| 管线化 | pipelining | 不等响应就连发请求 |
| 代理 / 网关 / 隧道 | proxy / gateway / tunnel | 三种转发者 |
| 源服务器 | origin server | 真正持有资源的那台服务器 |
| 无状态 | stateless | 协议不保存通信状态 |
| 内容协商 | content negotiation | 按客户端能力挑选返回内容 |
| 分块传输编码 | chunked transfer coding | 边生成边发送，用块大小标记 |
| 范围请求 | range request | 只要资源的一部分，支持断点续传 |
| 幂等 | idempotent | 执行一次和多次效果相同 |

## 答案与解析

1. 不是。角色是“每条连接”上的：同一台机器既可能当客户端，也可能当服务器。但在一条具体的 HTTP 通信线路上，两端的角色是确定的 —— HTTP 能明确区分谁在请求、谁在响应。
2. 请求报文：请求行（方法 + URI + 版本）、请求首部字段、空行、内容实体；响应报文：状态行（版本 + 状态码 + 原因短语）、响应首部字段、空行、实体主体。共同点是“起始行 + 首部 + 空行 + 主体”的对称结构，只差起始行写的内容。
3. ① 解析 URL（浏览器内部）；② DNS 解析域名 → IP（DNS，应用层）；③ TCP 三次握手建连（TCP，传输层）；④ 发送 HTTP 请求（HTTP，应用层）；⑤ 服务器处理；⑥ 返回 HTTP 响应；⑦ 浏览器解析渲染并继续请求子资源。
4. DNS 提供域名到 IP 地址的解析（也可反查）。计算机之间通信实际靠 IP 地址，但人记不住数字串，所以用域名，再由 DNS 翻译。计算机更擅长处理数字，人更擅长记字母。
5. `SYN`、`SYN/ACK`、`ACK`。TCP 负责可靠传输，要先确认双方都能正常收发、并同步序号，之后才能保证 HTTP 报文按序、不丢地送达；HTTP 本身不管“送不送得到”。
6. HTTP 是 TCP/IP 协议族这个**协议族**的一个**子集**，位于**应用层**；TCP/IP 采用**分层**设计，HTTP 只负责应用层的语义，传输交给 TCP、寻址交给 IP。
7. 应用层（HTTP、DNS、FTP）、传输层（TCP、UDP）、网络层（IP、ARP、ICMP）、链路层（以太网、网卡驱动）。
8. 封装是指发送端每经过一层就给数据打上该层的首部，像套娃一样包起来；接收端每经过一层就把对应首部拆掉。应用层加 HTTP 首部，传输层加 TCP 首部（序号、端口），网络层加 IP 首部（IP、MAC），链路层加以太网帧头帧尾。
9. URI 是“统一资源标识符”，回答“这个东西是什么”，用字符串标识某个资源；URL 是“统一资源定位符”，回答“这个东西在哪里”，**URL 是 URI 的子集**。绝对 URI 七部分：协议方案名、登录信息、服务器地址、服务器端口号、带层次的文件路径、查询字符串、片段标识符。
10. 不会。片段标识符只在浏览器内部用于定位页面内的锚点，不会放进 HTTP 请求的 URI 里，服务端永远收不到；需要靠 JS 读取 `location.hash`。
11. IP 地址是节点被分配的**逻辑**地址，可以变换；MAC 地址是网卡所属的**固定物理**地址，基本不变。IP 间通信依赖 MAC 地址，而中转时需要知道下一跳设备的 MAC，**ARP 就是根据 IP 地址反查出对应 MAC 地址**的协议。
12. 报文主体是报文中空行之后的那段字节流；实体主体是“作为有效载荷被传输的数据”的内容部分。**通常两者相等**；只有传输中进行了编码（如 gzip 压缩、分块传输）导致实体内容变化时，才会产生差异。
13. 不能同时用，二者互斥。`Content-Length` 要求事先知道主体长度；分块传输正是用于“长度未知、边生成边发送”的场景，用每块的十六进制大小标记边界，以 `0` 块结束。另外，对实体主体做内容编码传输时也不能再用 `Content-Length`。
14. 请求头是从客户端发往服务器时使用的首部，补充请求信息、客户端信息、内容优先级，如 `Host`（目标主机）、`User-Agent`（客户端信息）、`Accept`（可接受的媒体类型）；响应头是服务器返回响应时使用的首部，补充响应信息与对客户端的要求，如 `Location`（重定向目标）、`ETag`（实体标识）、`Server`（服务器软件信息）。
15. 请求发送到服务器时，主机名已被替换为 IP 地址。若同一 IP 下用虚拟主机部署了多个域名，服务器无法判断请求的是哪个站点，`Host` 就是用来补上主机名的 —— 这也是它成为 1.1 中唯一必需请求首部的原因。
16. `Referer` 告知服务器请求的原始资源 URI，即“从哪个页面点过来的”，常用于统计与防盗链。但原始 URI 的查询字符串可能含 ID、密码等保密信息，写进 `Referer` 转发给其他服务器就可能导致泄露，所以出于安全考虑可以不发送。另外它的正确拼写其实是 Referrer。
17. `ETag` 是服务器给每份资源分配的唯一性字符串标识，用于缓存校验（配合 `If-None-Match`）和范围请求（配合 `If-Range`）。强 ETag 只要实体有细微变化就改变；弱 ETag 只在资源发生根本改变时才变，值前加 `W/`。
18. 301 永久重定向，应更新书签；302 临时重定向，书签不更新；303 明确要求用 GET 去取另一个 URI；307 临时重定向且**不会把 POST 变成 GET**。实践中浏览器常把 301/302 当 303 处理，自动把 POST 改成 GET 并丢掉请求体。
19. 304 Not Modified 表示客户端发的附带条件请求未满足条件 —— 资源没更新，缓存还能用，响应不含主体。它虽然属于 3XX，但和重定向无关，是缓存机制的一部分；触发条件是请求里带了 `If-Modified-Since`、`If-None-Match` 等条件首部。
20. 401 表示“你还没证明你是谁”，需要 HTTP 认证信息（BASIC / DIGEST），响应必带 `WWW-Authenticate`，浏览器会弹登录框；403 表示“我知道你是谁，但你无权访问”，服务器拒绝提供服务，不再要求认证。
21. 204 表示请求已成功处理但响应中不含实体主体，也不允许返回，用于“只需客户端上报、无需返回新内容”的场景；206 表示客户端做了范围请求，服务器成功返回了其中一部分，响应带 `Content-Range`，用于断点续传、视频拖动。
22. 500 表示服务器端执行请求时发生了错误（多为应用 bug 或临时故障）；503 表示服务器暂时超负载或正在停机维护，无法处理请求。503 最好配合 `Retry-After` 告知客户端多久后重试。
23. 本质区别是**语义**：GET 是“获取资源（读）”，POST 是“传输实体主体（写）”。参数放在 URL 还是 body、能否缓存、能否收藏、有无长度限制，都是从语义派生出来的规则；正因为 GET 只读，浏览器才敢缓存它、才敢让你把它存成书签。
24. 无状态是为了“更快地处理大量事务，确保协议的可伸缩性”：服务器不必为每个用户保存上下文，一台机器就能扛住海量请求。Cookie 通过在响应中 `Set-Cookie` 下发、请求中 `Cookie` 回传，让服务器能识别客户端。代价是：需要额外的存储与校验、Cookie 可能被窃取（所以要 `HttpOnly`、`Secure`、HTTPS），以及每个请求都要多带一段首部。

> 📖 **学完之后做什么**　① 用 `curl -v https://example.com` 看一遍真实的请求 / 响应首部；② 在浏览器 Network 面板里找一个 304、一个 302、一个带 `Set-Cookie` 的响应；③ 接着读原书第 5 章（代理与缓存）、第 7 章（HTTPS）、第 9 章（HTTP/2、WebSocket）。把这三块补上，HTTP 这条线就完整了。
